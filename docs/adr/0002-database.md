# ADR-002. PostgreSQL як основна СУБД

Статус: прийнято, 2026-11-03

## Контекст

Система зберігає публікації, авторів, теми, користувачів, елементи читацького списку, нотатки та історію змін статусів. Між публікаціями й авторами існує зв'язок «багато-до-багатьох».

Ключова операція системи, додавання публікації до читацького списку та зміна її статусу (`до читання → читаю → прочитано`), має вимоги, які залежать від можливостей СУБД:

- повторне додавання тієї самої публікації користувачем не створює дубля, навіть за одночасних запитів;
- зміна статусу та запис в історію виконуються в одній транзакції;
- перехід у «прочитано» фіксує дату й не змінюється повторним запитом, зокрема коли два запити надходять одночасно;
- публікація, знайдена в arXiv і Crossref, зберігається один раз: унікальність за DOI та за arXiv ID, причому будь-який із них може бути відсутній.

Також база обслуговує пошук за назвою й автором, агрегати за місяцями, а збір даних за розкладом пише в неї паралельно з обробкою запитів API. Для курсового проєкту потрібні міграції схеми, відтворення бази з нуля однією командою та публічне розгортання.

## Розглянуті варіанти

1. **SQLite.** Не потребує окремого сервера: база це файл, запуск і тести найпростіші. Підтримує транзакції, `UNIQUE`-обмеження, часткові індекси та `INSERT ... ON CONFLICT`. У режимі WAL читання не блокують запис. Обмеження: у кожен момент записує лише одне з'єднання, тому фоновий збір даних і запити API на запис конкурують за один замок; немає `SELECT ... FOR UPDATE`, і взаємне виключення доводиться будувати через `BEGIN IMMEDIATE`, тобто блокуванням усієї бази; зміна схеми через `ALTER TABLE` обмежена, і в Alembic потрібен режим пакетного перетворення таблиць; типи й функції для дат та повнотекстового пошуку скромніші. Для одного користувача цього було б достатньо, але фактична поведінка відрізнялася б від типового серверного середовища.

2. **PostgreSQL.** Окремий сервер, потребує запуску (локально через Docker Compose) і конфігурації. Дає блокування на рівні рядків (`SELECT ... FOR UPDATE`), MVCC (читання не блокують запис), часткові унікальні індекси, `INSERT ... ON CONFLICT`, `date_trunc` для агрегації за місяцями, розширення `pg_trgm` і `tsvector` для пошуку, повноцінний `ALTER TABLE` у міграціях. Доступна як керована служба на більшості майданчиків розгортання.

## Рішення

Використовувати PostgreSQL як основну СУБД, драйвер psycopg 3 через SQLAlchemy 2.0.

Ідемпотентність додавання до списку забезпечується обмеженням `UNIQUE (user_id, publication_id)` та `INSERT ... ON CONFLICT DO NOTHING`. Зміна статусу виконується в транзакції з блокуванням рядка елемента списку (`SELECT ... FOR UPDATE`). Дедуплікація публікацій спирається на часткові унікальні індекси за `doi` та `arxiv_id` (з умовою `WHERE ... IS NOT NULL`).

Інтеграційні тести та CI працюють із реальним PostgreSQL, а не з його емуляцією.

## Наслідки

Позитивні:

- вимогу коректності за одночасних звернень можна довести тестом на рівні бази, а не лише логікою застосунку;
- фоновий збір і запити API не блокують один одного;
- пошук і агрегати за місяцями виконуються засобами СУБД;
- схема змінюється звичайними міграціями Alembic без обхідних прийомів;
- середовище розробки, тестів і продакшену збігається, тому менше сюрпризів під час розгортання.

Негативні:

- для локальної роботи потрібен запущений PostgreSQL (Docker), початкове налаштування складніше, ніж із файлом SQLite;
- CI потребує сервісного контейнера з базою, тести повільніші й складніші в підтримці, ніж із SQLite в пам'яті;
- з'являється ще один компонент для розгортання, резервного копіювання, відновлення та керування секретами;
- умови безкоштовних тарифів керованих баз на майданчиках розгортання змінюються, тому їх треба перевірити перед розгортанням;
- `FOR UPDATE`, часткові індекси та `pg_trgm` прив'язують код сховища до PostgreSQL, і перехід на іншу СУБД стане дорожчим. Домен і сервіси від цього ізольовано, бо працюють через протоколи.

## Умова перегляду

Рішення варто переглянути, якщо:

- з'явиться вимога запускати проєкт без Docker та зовнішніх сервісів (наприклад, як локальний застосунок для одного користувача): тоді SQLite стане виправданою;
- на обраному майданчику розгортання не вдасться отримати PostgreSQL за прийнятних умов;
- пошук або аналітика виростуть настільки, що знадобиться спеціалізований сервіс (повнотекстовий рушій, сховище для аналітики).
