# ADR-010. Контейнеризація й розгортання

Статус: прийнято, 2026-11-16

## Контекст

Методичка вимагає, щоб повний стек (застосунок і база) піднімався однією командою, продукт був доступний за публічним URL із дійсним HTTPS, секрети не потрапляли в репозиторій, а резервна копія й відновлення були перевірені на практиці. Є три процеси застосунку: API, одноразові міграції схеми й збирач за розкладом.

## Розглянуті варіанти

Для середовища:

1. **PaaS (Render, Fly.io, Railway).** Готові HTTPS, керована база, деплой із репозиторію. Але умови безкоштовних тарифів змінюються й обмежені (сон неактивних сервісів, терміни життя бази), а резервні копії залежать від плану.
2. **Власний сервер із Docker Compose і Caddy.** Повний контроль, стек у репозиторії, HTTPS автоматично. Потрібні сервер, домен і адміністрування (оновлення ОС, копії).
3. **Kubernetes.** Надмірно для одного невеликого сервісу.

Для реєстру образів: Docker Hub (потрібні окремі секрети) проти GHCR (працює з `GITHUB_TOKEN`, образ поряд із кодом).

Для міграцій: виконувати при старті кожного екземпляра API проти окремого одноразового сервісу.

## Рішення

- Один образ (multi-stage, `uv sync --locked`, не від root) і три ролі за командою: API, `migrate`, `scheduler`.
- Compose для розробки й сервера; прод-конфігурація додається файлом `docker-compose.prod.yml` через `COMPOSE_FILE`. База назовні не публікується.
- Caddy як зворотний проксі з автоматичними сертифікатами.
- Образи публікуються у GHCR після злиття в `main` (теги `latest` і `sha-<коміт>`).
- Міграції виконує одноразовий сервіс, від якого залежать API й розклад.
- Копії: `pg_dump -Fc` за розкладом із ротацією, відновлення перевіряє `restore-check.sh`; CI відтворює це на кожному PR.
- Образ додатково дублюється в Docker Hub для зручного docker pull без автентифікації.

## Наслідки

Позитивні:

- стек відтворюється однією командою й однаково працює локально, в CI та на сервері;
- міграції не гоняться між екземплярами, схема готова до першого запиту;
- образ відкочується за тегом `sha-...`, а CI перевіряє сам образ (старт, healthcheck, копія та відновлення);
- платформа не прив'язана: той самий образ підходить для PaaS.

Негативні:

- сервер потрібно адмініструвати самим (оновлення ОС, диск, брандмауер);
- одна машина це єдина точка відмови: простій під час оновлення й після аварії;
- копії лежать на тому самому сервері, якщо їх не копіювати назовні;
- відкат образу не відкочує міграції схеми, їх відкат робиться вручну;
- пароль у `DATABASE_URL` складається з змінних, тому спецсимволи в ньому не підтримуються;
- публічний образ у реєстрі доступний усім: у ньому не повинно бути секретів (їх не копіює `.dockerignore`);
- Let's Encrypt має ліміти на кількість сертифікатів, тож часті перестворення домену можуть їх вичерпати.
- два реєстри й додаткові секрети (DOCKERHUB_TOKEN), які треба ротувати.

## Умова перегляду

Переглянути, якщо знадобляться кілька екземплярів API (тоді балансувальник і спільний стан), безвідмовність (керована база з реплікацією), або сервер стане тягарем (тоді PaaS).
