# ADR-008. Інтерфейс командного рядка й збір за розкладом

Статус: прийнято, 2026-11-12

## Контекст

Методичка вимагає CLI, що запускає збір даних, наповнення бази й формування звіту. ТЗ додає експорт читацького списку в BibTeX і збір за розкладом за запитами користувача. До цього збір, seed і створення адміністратора були окремими тимчасовими скриптами з власним читанням змінних середовища.

## Розглянуті варіанти

Для CLI:

1. **Typer (або Click).** Менше шаблонного коду, автодоповнення, гарний `--help`. Але нова залежність (Click, Rich), а перевірка поведінки потребує окремого тестового раннера.
2. **argparse зі стандартної бібліотеки.** Без залежностей, `main(argv)` тестується напряму. Більше ручного коду для підкоманд.

Для розкладу:

1. **Планувальник ОС (cron, Task Scheduler) чи контейнерний планувальник.** Не потрібен код. Але конфігурація живе поза репозиторієм, на Windows та в Linux різна, а запуск процесу щоразу повторює ініціалізацію.
2. **Бібліотека (APScheduler) або черга (Celery).** Гнучкі розклади й повтори. Потрібен брокер (Celery) або складніша модель життєвого циклу; для одного завдання це надмірно.
3. **Цикл у власному процесі (`scitracker schedule`).** Мінімум коду, поведінку видно в репозиторії й тестах, у Docker це окремий сервіс.

## Рішення

- CLI на `argparse`, консольна команда `scitracker` і `python -m scitracker`. Побічні ефекти (сесії БД, збір, пароль, потоки виводу) передаються через `Context`, тож обробники тестуються без мережі.
- Розклад це цикл `run_periodically` із глобальним інтервалом (за замовчуванням 6 годин). Збій запуску логується, розклад триває. SIGINT і SIGTERM завершують процес після поточного запуску.
- Збираються всі теми. Теми з однаковим запитом діляться одним раундом запитів до джерел. Тема, яку не вдалося зберегти, потрапляє у звіт з помилкою, решта збирається.
- Код завершення `collect` ненульовий, коли тему не вдалося зберегти або всі джерела недоступні для всіх тем.
- BibTeX: усі записи `@misc`, бо тип публікації не зберігається.

## Наслідки

Позитивні:

- один вхід замість трьох скриптів, зрозумілий `--help`;
- жодних нових залежностей;
- логіка розкладу й збору перевіряється модульними тестами;
- однакові запити різних користувачів не множать навантаження на arXiv і Crossref.

Негативні:

- розклад один для всіх тем, окремої частоти для користувача немає;
- якщо процес не працює, запуски пропускаються без надолуження;
- два процеси `schedule` можуть збирати одночасно: це не ламає дані (ADR-003), але подвоює запити до джерел, а блокування між процесами немає;
- довгий запуск не переривається сигналом, зупинка настає після його завершення;
- збираються лише останні N записів за темою, інкрементального збору (`since`) немає;
- BibTeX без типу публікації й журналу, імена записані як у джерелі, а ключі цитування не транслітеруються з кирилиці;
- `argparse` вимагає більше ручного коду, ніж Typer.

## Умова перегляду

Переглянути, якщо знадобляться різні розклади для користувачів, чи кілька працюючих екземплярів збирача (тоді блокування в БД або черга), чи довгі запуски, які треба переривати. Тоді доречний APScheduler або чергa завдань.
