# ADR-006. Ідемпотентність і паралельність ключової операції

Статус: прийнято, 2026-11-06

## Контекст

Ключова операція системи: додавання публікації до читацького списку й зміна статусу (`до читання → читаю → прочитано`). ТЗ вимагає: повторне додавання не створює дубля; перехід у «прочитано» фіксує дату й не змінюється повторним запитом; зміна статусу та запис в історію виконуються в одній транзакції. Клієнт може повторити запит через збій мережі, а два пристрої користувача можуть надіслати запити одночасно. Обидва випадки мають давати той самий результат, що й один запит.

## Розглянуті варіанти

Для зміни статусу:

1. **Оптимістичне блокування (стовпець версії).** Запис оновлюється, лише якщо версія не змінилася; при розбіжності клієнт або сервер повторює спробу. Не тримає блокувань, добре для рідкісних конфліктів. Але потрібен новий стовпець і міграція, а логіку повторів доведеться писати й тестувати.
2. **Рівень ізоляції SERIALIZABLE з повтором транзакції.** Коректність гарантує СУБД. Але помилки серіалізації виникають у непередбачених місцях, повтор потрібен для кожної операції, а поведінку важко пояснити.
3. **Песимістичне блокування рядка (`SELECT ... FOR UPDATE`).** Запит блокує рядок елемента списку на час транзакції; конкурент чекає і читає вже новий стан. Просто, передбачувано, не потребує змін схеми. Недолік: конкуренти чекають, а за помилки в коді блокування може триматися довше, ніж потрібно.

Для додавання до списку: «перевірити, потім вставити» (має гонку) проти `INSERT ... ON CONFLICT DO NOTHING` за унікальним обмеженням `(user_id, publication_id)`.

Для повторного запиту: повертати помилку 409 («вже виконано») проти повертати 200 з поточним станом (no-op).

## Рішення

- Додавання: `INSERT ... ON CONFLICT DO NOTHING RETURNING`, далі читання наявного рядка. Новий елемент повертає `201`, наявний `200`.
- Зміна статусу: `SELECT ... FOR UPDATE` за парою `(id, user_id)`, перевірка правил у домені, `UPDATE` і запис історії в тій самій транзакції. `COMMIT` робить обробник API після успішного сервісу; будь-який виняток закінчується відкатом.
- Повторний запит на той самий статус це no-op: `200`, історія не пишеться, `finished_at` не змінюється.
- Вибірки завжди фільтруються за власником, тому чужий елемент неможливо відрізнити від неіснуючого (`404`).
- Захист у глибину: `CHECK` у БД вимагає, щоб `finished_at` був заданий тоді й лише тоді, коли статус «прочитано».

## Наслідки

Позитивні:

- дубль неможливий навіть за одночасних запитів, бо його забороняє обмеження БД, а не код;
- два одночасні переходи в «прочитано» дають один запис історії й одну дату (перевіряє тест із вісьмома потоками);
- клієнт може безпечно повторювати запити;
- змін схеми не потрібно.

Негативні:

- конкуруючі запити до одного елемента виконуються послідовно; для особистого читацького списку це нікому не заважає;
- обробник API відповідає за `commit`: забутий коміт означає втрату змін, його ловлять тести API;
- клієнт не може відрізнити «зміна застосована» від «уже було так» за кодом відповіді (в обох випадках 200);
- після повернення з «прочитано» дата завершення скидається, попередня лишається лише в історії;
- блокування рядків прив'язує реалізацію до PostgreSQL.

## Умова перегляду

Переглянути, якщо один елемент списку почнуть змінювати багато користувачів одночасно (спільні списки), якщо блокування стануть вузьким місцем або якщо знадобиться розрізняти «застосовано» й «вже було» (тоді повертати різні коди чи поле у відповіді).
