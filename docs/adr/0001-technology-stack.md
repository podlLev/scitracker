# ADR-001. Технологічний стек проєкту

Статус: прийнято, 2026-11-01

## Контекст

Потрібно обрати інструменти для серверного застосунку, який збирає публікації з arXiv та Crossref, зберігає їх, дедуплікує та надає доступ через REST API й CLI. Проєкт виконується однією людиною за обмежений термін, тож стек має давати типобезпеку, автоматичні перевірки якості та просте розгортання. Вимоги до курсового проєкту також передбачають шарову архітектуру, міграції схеми, асинхронний збір даних, контейнеризацію і CI.

Рішення про конкретну СУБД винесено в окремий ADR, бо воно залежить від вимог до ключової операції і заслуговує окремого розгляду.

## Розглянуті варіанти

| Компонент               | Обрано                  | Альтернатива                     | Критерій вибору                                                                             |
|-------------------------|-------------------------|----------------------------------|---------------------------------------------------------------------------------------------|
| Мова                    | Python 3.13             | Python 3.11                      | Сучасний синтаксис типів (`type`, дженерики без `TypeVar`), методичка вимагає 3.12+         |
| Залежності              | uv + `pyproject.toml`   | Poetry, pip + requirements.txt   | Швидкість, лок-файл, один інструмент для середовища та залежностей                          |
| Web-фреймворк           | FastAPI                 | Flask, Django REST Framework     | Асинхронність із коробки, валідація через типи, автоматична специфікація OpenAPI            |
| Валідація               | Pydantic                | marshmallow, ручна валідація     | Інтеграція з FastAPI, схеми з анотацій типів                                                |

| Типи                    | mypy (strict)           | pyright                          | Вимога методички; зріла підтримка в CI                                                      |

## Рішення

Використовувати стек із таблиці вище. Вибір СУБД і спосіб пагінації фіксуються окремими ADR у відповідних PR.

## Наслідки

Позитивні:

- анотації типів скрізь: FastAPI, Pydantic, SQLAlchemy 2.0 і mypy працюють з одними й тими самими типами;
- асинхронний стек (FastAPI, httpx) дозволяє паралельно опитувати arXiv і Crossref;
- уся перевірка якості (ruff, mypy, pytest, import-linter) автоматизована й запускається однаково локально та в CI;
- SQLAlchemy не прив'язана до веб-фреймворку, тому доступ до даних можна використовувати і з API, і з CLI.

Негативні:

- FastAPI не надає адмінпанель, автентифікацію й ORM «з коробки», як Django; їх доведеться збирати й підтримувати самостійно;
- асинхронний код складніший у налагодженні та тестуванні, ніж синхронний;
- SQLAlchemy 2.0 має вищий поріг входу, ніж Django ORM, і більше шаблонного коду;
- велика кількість інструментів означає більше конфігурації й більше залежностей для оновлення;
- mypy у суворому режимі уповільнює розробку, особливо при роботі з бібліотеками без типів.

## Умова перегляду

Рішення варто переглянути, якщо:

- збір даних виявиться суто пакетним без вимог до паралельності, тоді синхронний стек буде простішим;
- з'явиться потреба в адмінпанелі та складних ролях, які Django дав би готовими;
- один із ключових інструментів (наприклад, uv) втратить підтримку або виявиться несумісним з обраним майданчиком розгортання.
