# ADR-012. Кешування відповідей статистики й публічних тем

Статус: прийнято, 2026-11-14

## Контекст

Агрегації `/stats/by-topic` і `/stats/top-authors` рахуються на льоту (ADR-007) і дорогі відносно решти запитів, а змінюються лише після збору (`collect`) або зміни тем. `GET /topics` повертає однаковий список публікацій для всіх. Водночас видимість тем залежить від користувача (приватні теми), тому помилка в ключі кешу означала б витік чужих даних. Збирач працює в окремому процесі (сервіс `scheduler` на Railway), а API в іншому.

## Розглянуті варіанти

Для сховища: пам'ять процесу проти Redis. Для інвалідації: лише TTL проти TTL і скидання за подією. Для рівня кешу: HTTP-кеш (`Cache-Control`, ETag) проти кешу результатів сервісу. Для обсягу: кешувати все проти кешувати вибірково.

## Рішення

- Порт `Cache` і `make_key` у `services/cache.py`, адаптер `InMemoryTtlCache` у `cache/memory.py`, `NullCache` для вимкненого режиму. Час передається ззовні.
- Кешуються результати сервісу (`Dynamics`, список авторів, публічні теми), конвертація у відповідь лишається в API.
- Кешуємо лише `GET /stats/by-topic`, `GET /stats/top-authors`, `GET /topics`. Не кешуємо `/stats/reading`, `/feed`, `/reading-list`, `/me/*` і будь-які зміни: це особисті дані, які мають бути миттєво актуальними. Користувача в `get_current_user` не кешуємо, щоб видалення акаунта й зміна ролі діяли негайно (ADR-005).
- Ключ: `простір:sha256(user_id + параметри)`. `user_id` це обов'язковий іменований аргумент `make_key`, для гостя `None`. Для статистики в ключ входить і поточна дата, бо від неї залежить типовий період.
- Єдиний TTL (`CACHE_TTL_SECONDS`, 60 с), обмеження кількості записів (`CACHE_MAX_ENTRIES`, LRU).
- Скидання за подією: після коміту в `POST/DELETE /topics` скидаються простори `topics` і `stats`.
- Одночасні промахи за одним ключем рахують значення один раз (single-flight). Лічильник поколінь не дає записати значення, обчислене під час інвалідації.
- Помилки (404, 422) не кешуються. Відповіді мають заголовок `X-Cache: HIT|MISS` для демонстрації й вимірювань.
- Вимикається змінною `CACHE_ENABLED=false`, що дає порівняння до/після без зміни коду.

## Наслідки

Позитивні:

- повторні запити статистики обходяться без запитів агрегації до БД (числа в `docs/performance/stats-cache.txt`);
- витік між користувачами неможливий за побудовою ключа й перевіряється тестами;
- вимкнення кешу не змінює поведінку, лише швидкість.

Негативні:

- **Збір даних відбувається в іншому процесі, тож скинути кеш API після `collect` неможливо.** Свіжість статистики після збору гарантує лише TTL: до 60 с застарілих даних;
- кеш у пам'яті процесу не спільний між екземплярами: за кількох екземплярів API скидання після зміни теми діє лише в тому, що обробив запит, а інші віддають застаріле до кінця TTL. Для масштабування потрібен Redis;
- перезапуск скидає кеш, перший запит після нього повільний;
- кешовані значення не можна змінювати (покладаємось на дисципліну, не на копіювання);
- до 60 с користувач може бачити тему, якою щойно відмовилися ділитися (немає такої можливості в API, але для нових сценаріїв це треба перевіряти).

## Умова перегляду

Переглянути, якщо з'являться кілька екземплярів API (Redis і спільна інвалідація), якщо вимоги до свіжості після збору зростуть (сигнал із збирача, наприклад версія даних у БД), або якщо профілювання покаже вузьке місце в інших маршрутах.
